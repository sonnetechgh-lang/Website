# Codex Instructions

## Mandatory Site-Wide POS Visual Consistency

The newly created interactive POS demo is the single visual source of truth for every POS-related reference across the homepage and the entire website.

Do not use generic POS renders, stock dashboards, unrelated interfaces, AI-generated software screens, or decorative device mockups containing fake UI.

### This Requirement Applies To

- Homepage hero visuals
- Featured POS demo section
- POS service cards
- Industry sections
- Case-study images
- Feature illustrations
- CTA sections
- Demo thumbnails
- Video covers
- Page banners
- Social-sharing images
- Mobile and desktop device mockups
- Background interface graphics
- POS-related icons and animations
- Dedicated POS, inventory, and management-system pages

### Visual Source Of Truth

Use the supplied Aggie Vet reference screenshots for the interface structure and the public Sonnet POS demo for the final visual system.

All POS visuals must consistently use:

- 256px white desktop sidebar
- 65px white top navigation bar
- Inter typography
- `#F9FAFB` application background
- `#0284C7` primary accent
- `#E0F2FE` active-navigation background
- 8px control radii
- Subtle grey borders and shadows
- 32px desktop content padding
- Colourful dashboard KPI cards
- Clean white data tables
- Status badges for stock conditions
- Product cards with name, category, price, and stock
- Two-column POS catalogue and cart layout
- Matching reports, inventory, and receipt styling
- Responsive mobile navigation and stacked layouts

### Branding Rule

Do not publicly reproduce Aggie Veterinary Consult's branding or operational information unless explicit permission has been provided.

For the public demo, replace the client identity with a neutral presentation such as:

- Sonnet POS Demo
- Demo Retail Store
- Sample Business

Use fictional:

- Products
- Customers
- Telephone numbers
- Staff names
- Receipt numbers
- Transactions
- Stock quantities
- Credit balances
- Sales figures
- Business addresses

The interface design should remain faithful to the working system while all public data remains fictional.

### Device Mockups

Device mockups are permitted only when their screens display an actual view from the new Sonnet POS demo.

For example:

- A laptop may display the demo dashboard
- A tablet may display inventory management
- A desktop may display reports
- A mobile device may display the responsive POS interface
- A thermal printer mockup may display the matching demo receipt

Do not place a generic third-party dashboard inside a device frame.

### Screenshot And Asset Generation

Where static imagery is required:

1. Run the public demo using fictional data.
2. Capture the actual rendered interface.
3. Use that capture directly or place it inside a restrained device mockup.
4. Preserve the original proportions and legibility.
5. Update the image whenever the corresponding demo interface changes.

Do not manually redraw a screen in a design tool if an authentic application capture can be used.

### Animation Requirements

Any animated POS presentation must animate the real demo interface.

Suitable sequences include:

- Dashboard KPIs appearing
- Switching between dashboard modules
- Searching for a product
- Adding a product to the cart
- Selecting a customer
- Changing the payment method
- Completing a simulated sale
- Opening the receipt
- Switching to reports

Animations must not introduce interface elements that do not exist in the demo.

### Component Reuse

Where practical, build website product previews from the same design tokens and reusable components used by the interactive demo.

Avoid maintaining two visually different representations of the POS system.

If direct component reuse is not practical, create shared tokens for:

- Colours
- Typography
- Spacing
- Radii
- Shadows
- Icons
- Status colours
- Table styling
- Buttons
- Form controls

### Content Consistency

Feature descriptions must correspond to something visitors can see in the demo or to a clearly labelled custom capability.

Do not advertise a visible feature using a screenshot from another system.

If a capability is not included in the public demo, label it appropriately:

- Available on request
- Configurable for your business
- Supported in custom deployments
- Coming soon

### Asset Audit

Before completing the redesign, search the entire repository for:

- Existing POS screenshots
- Generic dashboard images
- Stock POS renders
- AI-generated interface images
- Old product mockups
- Placeholder dashboard graphics

Replace or remove every visual that conflicts with the new demo.

Do not leave outdated POS imagery on secondary pages, hidden sections, metadata, social-sharing images, or mobile layouts.

### Acceptance Criteria

The requirement is complete only when:

- Every POS visual can be traced to the new demo interface
- No generic POS dashboard remains anywhere on the website
- Desktop, tablet, and mobile mockups display the same product language
- Receipt visuals match the demo receipt
- All public screenshots use fictional data
- Client branding and private operational information are excluded
- Feature descriptions match demonstrated capabilities
- Social-sharing images also use the new demo outlook
- The website and demo feel like one product ecosystem
- A repository-wide asset search confirms that outdated renders have been removed
